## Follow-ups recorded, not fixed here

Both are real, both were found during this screen's verification, and neither belongs to this screen's file ownership.

- **FUP-01 — The sticky header is 80% opaque with no backdrop blur, so page content bleeds through it.** `home-header.tsx` renders `rgba(16,20,23,0.8)` with no `backdrop-filter`; at 375px wide the gold `8.000.000 VNĐ` scrolls visibly across the nav labels. The tester checked whether this screen caused it and it does not: the computed header background is **identical** on `/` and `/awards-information` at both widths, and the header band's non-background pixel share at 375px is **higher on the homepage (22%) than here (10%)**. It is a pre-existing defect in the shared header that this screen merely re-exposes, `home-nav.tsx`/`home-header.tsx` are read-only under ORCH-03, and the fix belongs on a ticket against the shared header where it can be judged against `/` first.
- **FUP-02 — The quantity-unit column is fixed at `w-[60px]`, which suits the VI copy and cramps the EN.** Reviewer suggestion S-10 proposed `max-w-[88px]`. Skipped deliberately: `max-w` lets `Cá nhân` collapse onto one line, changing the VI rendering the frame specifies and the tester pinned by measurement. Fixing the untested secondary locale by moving the design-specified default locale is the wrong trade at this stage. Revisit when EN gets its own visual pass.

## Orchestrator decisions

Numbered `ORCH-xx` deliberately — `DEC-###` is a reserved canonical spec token and must not be reused here.

- **ORCH-01 — Track B runs before Track A, not concurrently.** `.claude/rules/momorph/momorph-development.md` allows the two tracks to run concurrently after the gate. Here Track B's entire surface is the dictionary type + copy + data module (assumption A2), which Track A must import to typecheck. Sequencing them costs minutes and removes a guaranteed compile race; the rule's concurrency is an allowance, not an obligation.
- **ORCH-02 — Single Track A worker, section mode not used.** The screen is one cohesive column of six structurally identical cards. Fanning out sections would create six workers competing for one `award-detail-card.tsx`. One `momorph-ui-implementer` in `screen` mode owns the whole surface.
- **ORCH-04 — The deep-link active item is seeded post-hydration, and a ~290ms transient is accepted.** Added 2026-09-06 after the tester measured `[[0,"top-talent"],[290,"mvp"]]` on `/awards-information#mvp` (reviewer finding S-13: the record and the code described two different mechanisms). A URL fragment is never sent to the server, so the SSR HTML necessarily ships `AWARDS[0]` active; the correction lands when React hydrates and the observer delivers. The 290ms is the route's time-to-interactive, not an animation — the mount-time scroll was already `behavior: "auto"` throughout, and there is no `scroll-behavior`/`scroll-smooth` anywhere in `app/` or `lib/`. This is a fixed cost, which is why a `--repeat-each=10` run was stable rather than jittery. Rejected alternatives: a lazy `useState` initialiser reading `location.hash` renders `top-talent` on the server and `mvp` on the client — a hydration mismatch that fails ID-13's zero-console-errors assertion, trading a cosmetic flash for a real regression; `useSyncExternalStore` with a `getServerSnapshot` still yields `AWARDS[0]` on the hydration render; rendering nothing active on the server trades a wrong highlight on deep links for no highlight on every ordinary load. A CSS `:target`/`:has()` rule would fix first paint but duplicates the source of truth and leaves `aria-current` lagging regardless — it fixes what is seen, not what a screen reader announces. Accepted: end state correct, sub-second, deep-link only.
- **ORCH-05 — `app/_components/kudos-promo.tsx` may take an optional `maxWidthClass` prop.** Added 2026-09-06. The "compose `KudosPromo` unchanged" mandate above means *do not fork it*; the component self-constrains at `max-w-[1224px] lg:px-36` → 936px content, so no wrapper can widen it, and at 936 the body copy runs underneath the KUDOS logo on this screen. One component with a defaulted prop honours the mandate's intent; a second copy would not. The homepage passes nothing and renders byte-identically (verified from rendered HTML and by direct measurement: `max-w-[1224px]`, card 252→1188 w936, unchanged). This screen passes `max-w-[1440px]` → 1152 content at x=144→1296, matching the frame's 144→1295. The two screens genuinely differ: the homepage frame is a 1512 artboard, this one is 1440.
- **ORCH-06 — The menu↔card gap is distributed space, not a declared 80px gap.** Added 2026-09-06 after the journal-writer flagged that this reading existed only in an agent report and in conversation, never in a durable artifact. The frame lays `mms_B` out with `space-between` and an **80px minimum** gap; the 121px that actually separates the category menu from the card column is *leftover* space the layout distributes, not a fixed value. The first implementation declared only the 80px minimum, which is precisely where the measured 41–42px left-edge deficit came from. The fix was therefore `lg:justify-between` on the body row plus `lg:grow-0 lg:basis-[853px]` on the card column — restoring the mechanism — not a hardcoded +42px nudge. Verified after the change: nav 144→322, cards 443→1296, text column 821 against the frame's 819. Recorded because the next person to touch this layout will otherwise read 121px as a magic number and hardcode it.
- **ORCH-03 — `home-nav.tsx` and `site-footer.tsx` are read-only for this task.** Their selected-state derivation already handles this route. Any edit there would ripple into the green homepage suite and is out of file ownership.
