# Next.js 16.3.4 Conventions for Login Page (Supabase Google OAuth)

Source of truth: `node_modules/next/dist/docs/` (read directly, not from memory). Next 16.3.4, React 19.2.8, TS5, App Router. Project already has `proxy.ts` and `app/layout.tsx` — checked both against docs.

## 1. proxy.ts (middleware renamed)

Doc: `01-app/01-getting-started/16-proxy.md`, `01-app/03-api-reference/03-file-conventions/proxy.md`, `.../middleware.md` (now a stub pointing to proxy).

- Next 16: `middleware.ts` file convention is **deprecated**, renamed to `proxy.ts`. Functionality unchanged, only file/export name changed. Codemod: `npx @next/codemod@canary middleware-to-proxy .`
- Location: project root or `src/`, same level as `app`/`pages`. **Project's `proxy.ts` at root is correct.**
- Export shape — named `proxy` or default export, single function, optionally `async`:
  ```ts
  export function proxy(request: NextRequest) {
    return NextResponse.redirect(new URL('/home', request.url))
  }
  export const config = { matcher: '/about/:path*' }
  ```
  Params: `(request: NextRequest, event: NextFetchEvent)` — declare only what you use. Shorthand type: `NextProxy` from `next/server`.
- **Runtime**: Proxy defaults to Node.js runtime in v16 (v15.5 made Node runtime stable/optional; v16 makes it default). The `runtime` route-segment-config option is **not available** in proxy files — setting it throws.
- **Redirects ARE supported**: `NextResponse.redirect(new URL(...))` is the documented pattern, used directly in the Auth guide's own proxy example (see below). `Response.redirect` also works.
- **Cookies**: full read/write via `request.cookies` / `response.cookies` (get/getAll/has/set/delete). This is how Supabase SSR session refresh works in proxy.
- **NOT allowed / cautions**:
  - `fetch` `options.cache` / `options.next.revalidate` / `options.next.tags` have no effect in proxy.
  - Proxy is *not* for slow data fetching — "not intended for slow data fetching," should not be the sole session/auth solution (optimistic checks only).
  - Setting `runtime` config throws.
  - Server Functions (`'use server'` actions) are NOT separate routes in the execution chain — they're POST requests to the route that uses them, so a proxy matcher excluding a path also skips Server Actions on that path. Verify auth inside every Server Action too, not just proxy.
  - Matcher values must be static/constant (statically analyzable at build time) — no dynamic variables.
- Auth-specific proxy pattern is directly documented in `01-app/02-guides/authentication.md` (Optimistic checks with Proxy section) — decrypt session cookie, redirect unauthenticated users off protected routes, redirect authenticated users off public-only routes (`/login`, `/signup`). This is literally the reference pattern for a login page's proxy guard.
- Project's current `proxy.ts` calls `updateSession(request)` from `@/lib/supabase/update-session` and returns the response — this matches the documented "session refresh only, no route protection yet" pattern; route protection via `NextResponse.redirect` is fully supported and is the documented idiom when the team decides to add it.

## 2. Route Handler at `app/auth/callback/route.ts`

Doc: `01-app/01-getting-started/15-route-handlers.md`, `01-app/03-api-reference/03-file-conventions/route.md`.

- File convention: `app/auth/callback/route.ts`, export named HTTP-method functions (`GET`, `POST`, etc.).
- **`params` is a Promise in v16** (async since v15.0.0-RC; sync access still works for back-compat but is deprecated). Same for page/layout `params`.
- **`searchParams` is not passed to Route Handlers as a prop** — Route Handlers read query via `request.nextUrl.searchParams` (a real `URLSearchParams` on `NextRequest`), unlike pages where `searchParams` is a Promise prop.
- Exact GET signature reading query + redirecting:
  ```ts
  // app/auth/callback/route.ts
  import { type NextRequest } from 'next/server'
  import { redirect } from 'next/navigation'

  export async function GET(request: NextRequest) {
    const code = request.nextUrl.searchParams.get('code')
    // ... call async exchange function ...
    redirect('/dashboard')
  }
  ```
  (Verbatim doc example for redirect in a route handler: `import { redirect } from 'next/navigation'; export async function GET(request: Request) { redirect('https://nextjs.org/') }` — route.md "Redirects" section.)
- If the route is dynamic (e.g. `[id]`), `context.params` is a Promise: `{ params }: { params: Promise<{ id: string }> }`, or use the typed `RouteContext<'/path/[id]'>` global helper (generated by `next dev`/`build`/`typegen`).
- Cookies inside route handlers: `const cookieStore = await cookies()` from `next/headers` — get/set/delete all work here (route handlers, unlike Server Components, CAN set cookies).
- `GET` handlers are **dynamic by default** in v16 (not cached) unless `export const dynamic = 'force-static'`.

## 3. Server Actions — Google OAuth sign-in redirect

Doc: `01-app/01-getting-started/07-mutating-data.md`, `01-app/02-guides/server-actions.md`, `01-app/03-api-reference/04-functions/redirect.md`.

- Convention: `'use server'` directive at top of function or top of file. Server Functions used with `<form action>` / `<button formAction>` become Server Actions automatically (wrapped in `startTransition`).
- **`redirect()` throws** a `NEXT_REDIRECT` control-flow exception and terminates rendering/execution of the segment. Explicit doc rule: **"redirect should be called outside the try block when using try/catch statements"** (stated twice in redirect.md, once as "Behavior"). So:
  ```ts
  'use server'
  export async function signInWithGoogle() {
    let url: string
    try {
      url = await getGoogleOAuthUrl() // may throw
    } catch (e) {
      // handle/log, do NOT redirect here
      throw e
    }
    redirect(url) // outside try/catch — required
  }
  ```
- `redirect` accepts **absolute/external URLs** — explicitly documented: "redirect also accepts absolute URLs and can be used to redirect to external links." This directly supports redirecting to Google's OAuth consent screen.
- In a Server Action, redirect **defaults to `type: 'push'`** (vs. `'replace'` everywhere else). Can override via `redirect(path, RedirectType.replace)`.
- Server Action redirect behavior: "performs a client-side navigation when JavaScript is available. For progressive enhancement form submissions, it serves a 303 HTTP redirect response. Otherwise 307." (redirect.md, top). For an external OAuth redirect this effectively means: with JS enabled the client navigates via the returned redirect signal; without JS, a real 303 HTTP redirect is served to the browser — either way it lands on Google's URL.
- Security: doc explicitly warns Server Functions are reachable via **direct POST requests**, not just app UI — "Always verify authentication and authorization inside every Server Function." For a sign-in action this is less about authz (anyone can start OAuth) and more general framework posture — no special exemption for auth-initiating actions.
- CSRF: Next enforces Origin/Host check on Server Action POSTs automatically (server-actions.md) — no extra code needed, but if fronted by a proxy/CDN with a different origin, configure `experimental.serverActions.allowedOrigins`.

## 4. Typed route helpers — `LayoutProps`, `PageProps`

Doc: `01-app/01-getting-started/03-layouts-and-pages.md` ("Route Props Helpers"), `.../file-conventions/layout.md` ("Layout Props Helper"), `.../file-conventions/page.md` ("Page Props Helper"), `.../config/02-typescript.md` ("Route-Aware Type Helpers").

- **`LayoutProps<'/route'>`** and **`PageProps<'/route'>`** are globally available TypeScript helpers (no import needed) that infer `params`, `searchParams` (Page only), and named parallel-route slots from the literal route string.
  ```tsx
  export default async function Page(props: PageProps<'/blog/[slug]'>) {
    const { slug } = await props.params
  }
  export default function Layout(props: LayoutProps<'/dashboard'>) {
    return <section>{props.children}{/* props.analytics if @analytics slot exists */}</section>
  }
  ```
- **These are generated during `next dev`, `next build`, or `next typegen`** — a separate mechanism from `typedRoutes`. They live under "Route-Aware Type Helpers" alongside `RouteContext` (for route handlers).
- **`typedRoutes` is a DIFFERENT, opt-in-only config flag** (`next.config.ts: { typedRoutes: true }`), stable (renamed from `experimental.typedRoutes`). It only affects **`<Link href>` static typing and `next/navigation` push/replace/prefetch** — it does NOT gate `PageProps`/`LayoutProps`/`RouteContext`, which are always generated regardless.
- **Checked the project**: `next.config.ts` has no options set — `typedRoutes` is **NOT enabled**. Yet `app/layout.tsx` already uses `LayoutProps<'/'>` successfully — this is expected and correct, since `LayoutProps` doesn't depend on `typedRoutes`.
- Not required to use these helpers — plain inline prop types (`{ children }: { children: React.ReactNode }`) still work — but they're the documented idiom in v16 examples and the project has already adopted the convention for layout.tsx; recommend using `PageProps<'/route'>` for pages too for consistency.
- Static routes resolve `params` to `{}`.

## 5. `cookies()` — async status and read/write rules

Doc: `01-app/03-api-reference/04-functions/cookies.md`, `01-app/01-getting-started/07-mutating-data.md` (Cookies section), `.../file-conventions/route.md`, `.../file-conventions/layout.md` (Caveats → Request Object).

- **`cookies()` is fully async** — has returned a Promise since v15.0.0-RC. Must `await cookies()`. (Sync-with-warning back-compat existed for the v14→v15 transition but is on the deprecation track — always await in new code.)
- **Read**: works in Server Components (reading the incoming request's cookies), Server Functions/Actions, and Route Handlers.
- **Write (`.set`/`.delete`)**: only supported in **Server Functions (Actions)** and **Route Handlers** — NOT in Server Component render. Reason given: "Setting cookies is not supported during Server Component rendering... HTTP does not allow setting cookies after streaming starts."
- Reading `cookies()` in a layout or page opts that route into **dynamic rendering** (Request-time API).
- Direct applicability to plan: reading `NEXT_LOCALE` in a Server Component:
  ```ts
  import { cookies } from 'next/headers'
  export default async function Page() {
    const locale = (await cookies()).get('NEXT_LOCALE')?.value
  }
  ```
  Writing it from a Server Action:
  ```ts
  'use server'
  import { cookies } from 'next/headers'
  export async function setLocale(locale: string) {
    (await cookies()).set('NEXT_LOCALE', locale)
  }
  ```
  Setting/deleting a cookie in a Server Action automatically **re-renders the current route server-side** so UI reflects the new cookie value in the same round trip (mutating-data.md, cookies.md) — no manual `revalidatePath` needed just for the locale switch, though revalidate if locale changes affect cached data.
- `.delete()` additionally requires same-domain/protocol match to `.set()`.

## 6. i18n without a library — cookie-based, non-routing strategy

Doc: `01-app/02-guides/internationalization.md`.

**Gap flagged**: the official guide is written entirely around **path-segment routing** (`app/[lang]/...`, proxy redirecting `/products` → `/en-US/products`, `generateStaticParams` per locale, `next/root-params` for reading `lang`). There is **no section describing a cookie-based, non-path-segment locale strategy** — the guide assumes locale-in-URL is the strategy. This is a genuine doc gap for this project's stated approach (no locale path segments).

What can be soundly inferred/combined from adjacent, authoritative docs instead:
- Dictionary/localization pattern (dictionaries object + `getDictionary(locale)` loading via dynamic `import()`, guarded with `server-only`) is framework-agnostic and applies identically whether locale comes from a URL segment or a cookie — just swap the source of `locale` from `params.lang` to `cookies().get('NEXT_LOCALE')`.
- Since there's no `[lang]` segment, `next/root-params` (which only exists for **dynamic segments above the root layout**) does not apply — read the cookie directly via `cookies()` in Server Components/layout instead, per section 5 above.
- No official `next-cookie-i18n` helper exists in these docs; the listed community libraries (`next-intl`, `next-international`, `paraglide-next`, etc.) are all still oriented at the routing model. Confirm with the team whether a small in-house cookie+dictionary utility (no dependency) is acceptable — this fits YAGNI/KISS better than pulling in a routing-focused i18n library for a single cookie toggle.

## 7. next/image — local imports, width/height/priority/fill

Doc: `01-app/01-getting-started/12-images.md`, `01-app/03-api-reference/02-components/image.md`.

- Local static import (logo, wordmark, etc.) is the recommended path for images bundled in the app: `import Logo from './logo.png'; <Image src={Logo} alt="..." />` — Next auto-infers `width`/`height`/`blurDataURL`. No manual width/height needed for statically imported images.
- For images in `public/` referenced by string path (e.g. `/logo.png`), **`width` and `height` are required** unless `fill` is used.
- **`fill`**: boolean, image expands to fill parent; parent **must** have `position: relative|fixed|absolute`. Good for the full-bleed hero background. Use `objectFit` (via `style` or Tailwind `object-cover`) to control cropping.
- **BREAKING CHANGE in v16.0.0 — `priority` prop deprecated, replaced by `preload`**:
  > "Starting with Next.js 16, the `priority` property has been deprecated in favor of the `preload` property in order to make the behavior clear." (image.md, version history: `v16.0.0: qualities default changed to [75], preload prop added, priority prop deprecated, dangerouslyAllowLocalIP config added, maximumRedirects config added.`)
  - New prop: `preload={true|false}` (default `false`). Use for the LCP/above-the-fold image (the hero background is the clear candidate: `preload`).
  - Doc caveat: prefer `loading="eager"` or `fetchPriority="high"` over `preload` in most cases; don't combine `preload` with `loading` or `fetchPriority`.
  - **Old training-data pattern `<Image priority />` still works but is deprecated — use `preload` in new code.**
- Other relevant v16 image config changes: `qualities` default changed to `[75]` (was broader before); `dangerouslyAllowLocalIP` and `maximumRedirects` config added — check if remote/local network image sources need these.
- Remote images (none apparently planned here) require `next.config.ts` `images.remotePatterns`.

## 8. Metadata — page-level title

Doc: `01-app/01-getting-started/14-metadata-and-og-images.md`, layout.md "Examples → Metadata".

- Convention unchanged from prior versions: export a static `Metadata` object from `page.tsx` or `layout.tsx`:
  ```tsx
  import type { Metadata } from 'next'
  export const metadata: Metadata = { title: 'Login', description: '...' }
  ```
- `metadata`/`generateMetadata` exports are **Server Component only**.
- Do **not** hand-write `<title>`/`<meta>` tags in the root layout — use the Metadata API so streaming/dedup is handled.
- v16 nuance: **streaming metadata** — for dynamically rendered pages, Next streams `<head>` metadata separately once `generateMetadata` resolves (doesn't block UI), except disabled for known bot user agents (Twitterbot, Slackbot, Bingbot) which get blocking metadata. Static metadata objects (not `generateMetadata`) on a login page are simple and unaffected by this streaming nuance since they resolve immediately.
