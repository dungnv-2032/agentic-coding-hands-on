### Route, auth, and the modal question

- Q: The frame is a centred dialog over a dimmed page. Intercepting/parallel route for true modal-over-board, or a normal page? → A: **A normal page at `/kudos/new`.** The shipped Live Board links there with a plain `<a href="/kudos/new">`, and F004's `K-22` asserts exactly that hard navigation; an intercepting route would work against a ratified test. "Modal closes" in the test cases (ID-45, ID-46) therefore means **navigate back to `/kudos`**. The dialog card itself is still rendered faithfully — centred, `#FFF8E1`, over the dimmed page background.
- Q: `ID-1` requires an unauthenticated visitor to be redirected to login or shown a login-required message. The Live Board is deliberately public. Is this route guarded? → A: **Yes — `/kudos/new` is guarded, and this is the first guard added since F001.** Writing a Kudos requires an identity, so unlike the read-only board there is a real thing to protect. `proxy.ts` currently guards only `/todo` and `/login`; `/kudos/new` joins `/todo`. This edits a shipped shared file, so the existing route-guard and callback-security suites are blast radius and must stay green. The public read surface (`/kudos`, `/kudos/[id]`, `/kudos/secret-box`) is **unchanged**.

### Sender identity — the consequential one

- Q: `sunners` has 9 rows and **0** with `auth_user_id` set, and `lib/kudos/viewer.ts` resolves `sunnerId` only via `auth_user_id = auth.uid()`. A compose screen needs a sender. → A: **Auto-provision a `sunners` row on first authenticated write** (the study's ranked option 1). It is the only option that works for the real Google-OAuth population rather than just the e2e fixture, and it keeps the actor session-derived — `sender_id` is never accepted from the client, matching `toggleKudosLike`, which takes no actor argument. Because `sunners.auth_user_id` is already `unique`, the provision is written as an upsert (`on conflict (auth_user_id) do nothing`) followed by a re-select, so a double-submit cannot create two rows.
- Q: The schema requires `department_id NOT NULL` and `avatar_url NOT NULL`. What does a freshly provisioned Sunner get? No design answers this. → A:
  - `full_name` ← `user_metadata.full_name` / `name`, falling back to the email local-part. Never blank.
  - `avatar_url` ← `user_metadata.avatar_url` / `picture`, falling back to the committed `public/images/kudos/sample-avatar.png` — which is the design's own placeholder artwork (F004 assumption A3), not a fabricated photo.
  - `department_id` ← a **new seeded `Unassigned` department row with `filter_position NULL`**. It says plainly "this person's department is not known yet" instead of falsely asserting a real unit, and because `filter_position` is NULL it never enters the Phòng ban dropdown, so F004's `K-3` (which asserts exactly 50 options) stays green. Recorded as assumption **A1**.

### What the schema cannot hold yet

- Q: The anonymous checkbox `Gửi lời cám ơn và ghi nhận ẩn danh` has no backing column — `kudos` is exactly `id, sender_id, receiver_id, campaign, message, sent_at, heart_baseline`. → A: **New column `kudos.is_anonymous boolean not null default false`.** `ID-43`/`ID-44` additionally require that checking the box **reveals a text field for the anonymous display name**, which is not in the frame's visible render but is a real, twice-asserted requirement — so a second new column `kudos.anonymous_name text` holds it (nullable; only meaningful when `is_anonymous`). The Live Board card must then render an anonymous sender instead of the real one — a genuine change to the already-shipped F004 card. Every seeded row is non-anonymous, so F004's existing assertions are unaffected.
- Q: `Danh hiệu` → which column? → A: **`kudos.campaign`.** The helper text says the title "sẽ hiển thị làm tiêu đề Kudos của bạn", and the Live Board card already renders `campaign` as a centred label above the message (it showed `IDOL GIỚI TRẺ`). Same field. The column stays **nullable** — seeded and legacy rows have no title — while the compose form enforces it as required. No migration needed for this field.
- Q: `kudos`, `kudos_hashtags`, `kudos_attachments` and `sunners` have **only** SELECT policies, and no INSERT grant at all. → A: **A new migration adds INSERT policies and grants for all four**, each bridging to the session through the same `sunners.auth_user_id = (select auth.uid())` idiom already shipped for `kudos_likes`. Critically, `kudos.sender_id` references `sunners`, not `auth.users`, so the check must be `sender_id in (select id from sunners where auth_user_id = (select auth.uid()))` — that is what stops a client forging a kudos as somebody else. `kudos_hashtags` / `kudos_attachments` policies check ownership of the parent `kudos` row. There is deliberately **no UPDATE and no DELETE** policy: editing and deleting a Kudos are separate commissions (`Màn Sửa bài viết`, `Admin - Review content`).

### Rich text

- Q: The toolbar offers bold, italic, strikethrough, ordered list, link and quote (`C.1`–`C.6`, ID-27…ID-32), and `ID-31` requires a URL-entry dialog for the link. `kudos.message` is plain text and the Live Board renders it line-clamped. How is formatted content stored and re-displayed? The spec is **silent**. → A: **A hand-rolled JSON document model, serialized into the existing `message` text column, with a new `kudos.message_format` discriminator (`'plain' | 'doc'`).**
  - Rendering walks the document to **React elements** — never `dangerouslySetInnerHTML`, never an HTML string. This content is displayed to every anonymous visitor on the public board, so the XSS surface has to be zero by construction rather than by sanitising, and the repo has no sanitizer dependency (no `dompurify`, `sanitize-html`, `marked`, `remark`).
  - The discriminator is what keeps F004 intact: the 57 seeded rows stay `'plain'` and the shipped card renders them exactly as before, so F004's `kudos-body` assertions do not move. Only `'doc'` rows take the new renderer.
  - Document shape is deliberately minimal — a list of blocks (`paragraph` | `ordered-list-item` | `quote`), each holding inline runs with `bold` / `italic` / `strike` / `link href` / `mention` flags. No nesting beyond that. Anything richer is out of scope.
- Q: `@mention` — a real autocomplete, or a typing convention? → A: **A real autocomplete.** `ID-12`, `ID-13` and `ID-33` all require a suggestion list to appear as the user types after `@` and the chosen colleague to be inserted. It searches the existing `sunners` table; no new table. The chosen person is stored as a `mention` inline run carrying the sunner id, so it survives re-display, and the renderer prints the name — it does not re-resolve at read time.

### Images — overriding the study's recommendation

- Q: Real Supabase Storage upload, or reuse the committed sample assets the way F004 did? → A: **Real upload to Supabase Storage.** The study recommended reusing sample assets, and I am overriding that, because the study was written without MCP access and therefore had not seen the test cases. `ID-37` requires the file picker to open and *the chosen file* to appear as a thumbnail; `ID-21`/`ID-22` require a real `.jpg`/`.png` to upload successfully; `ID-23`/`ID-24` require a `.pdf` to be **rejected** with a format error. Substituting a stock sample image for whatever the user picked would make the thumbnail a lie and would make an honestly-written `ID-37` fail — it is exactly the "fake it / stopgap" the project rules forbid. `supabase/config.toml` already has `storage.enabled = true`; the migration declares a bucket with its own policies. File type is validated **both** client-side (for the immediate error) and server-side (because the client cannot be trusted).
- Q: Max images, and what happens at the limit? → A: **Max 5, and the `+ Image` button is HIDDEN once the fifth is added** (`ID-19`, `ID-20`, `ID-38`) — hidden, not disabled. Removing one brings it back (`ID-40`). Note this differs from the hashtag limit's behavior below, and the difference is what the test cases specify.

### Validation

- Q: Which fields are required, and what is the error copy? → A: **Người nhận, the message body, and Hashtag (min 1)** — error copy `Không được để trống`, verbatim (`ID-11`, `ID-14`, `ID-51`, `ID-52`). The recipient field additionally shows a **red border** (`ID-7`, `ID-50`). `Danh hiệu` is required from the frame's `*` but has no test case and no error copy authored, so it reuses the same `Không được để trống` string.
- Q: Stop at the first error, or show all? → A: **All required-field errors show simultaneously** (`ID-56`: "Hiển thị lỗi cho tất cả các trường bắt buộc: Người nhận, Nội dung, Hashtag").
- Q: Hashtag limit behavior? → A: **Max 5; attempting a sixth shows `Tối đa 5 hashtag`** (`ID-17`, `ID-53`) and the tag is not added. Tags render as removable chips (`ID-34`, `ID-35`, `ID-36`).
- Q: The `Gửi` button's state? → A: **Disabled while the required fields are empty, enabled once they are filled** (`ID-48`, `ID-49`). This is in addition to, not instead of, submit-time validation — the button state is a hint and the server still validates.
- Q: `Hủy`? → A: **Closes immediately and discards; no confirmation dialog** (`ID-45`: "Modal đóng / Dữ liệu không được lưu"). On a page that means navigating back to `/kudos`.
- Q: Successful `Gửi`? → A: **Validate → show a loading state → navigate back to `/kudos`** (`ID-46`, `ID-47`). The new Kudos must then be visible on the board, which is the honest end-to-end proof that the write landed.

### Shared chrome and i18n

- Q: Rebuild or compose the chrome? → A: **Compose unchanged** — `getPageContext()`, `HomeHeader`, `SiteFooter`, exactly as `/kudos` and `/awards-information` do.

## Assumptions

- **A1 — A seeded `Unassigned` department (`filter_position NULL`) backs auto-provisioned Sunners.** The schema demands a department, a freshly signed-in Google user has none, and the design offers no answer. `filter_position NULL` keeps it out of the Phòng ban dropdown so F004's 50-option assertion is untouched.
- **A2 — `Danh hiệu` is required and maps to `kudos.campaign`.** Required per the frame's `*`; the column stays nullable for pre-existing rows.
- **A3 — Anonymity hides the sender on the public board.** With `is_anonymous` true the Live Board card shows the anonymous display name (or a neutral label when none was given) in place of the sender chip. The receiver is always shown — anonymity protects the giver, not the recipient.
- **A4 — The body has no maximum length.** No `maxLength` appears anywhere in the CSV and no test asserts one, so none is enforced and no character counter is drawn, despite `D.1`'s stale name.
- **A5 — Uploaded images are the user's real files, stored in Supabase Storage**, not the design's `MM_MEDIA_Sample Image` placeholders. This deliberately diverges from F004's assumption A3, because that screen only ever *displayed* placeholder artwork whereas this screen's own test cases require the picked file to round-trip.

## Unresolved questions

1. **`Danh hiệu` has no spec item and no test case.** It is in the frame with a required `*` and is being built on that basis. Its error copy, max length, and whether it should appear in the `ID-3` field order are all unauthored. Needs a design/spec refresh to catch up with the `1688:*` nodes.
2. **`D.1` promises a character counter** ("Gợi ý và bộ đếm ký tự") that the frame does not draw and no test asserts, with no max length authored anywhere. Not built. If a limit is wanted, both the number and the counter's placement need designing.
3. **Two in-scope companion frames have no authored spec content** — `zJzaC9GgXt` (recipient dropdown) and `5c7PkAibyD` (error state). Their behavior is being derived from the test cases instead; a spec pass on them would confirm or correct that.
4. **The anonymous display-name field is required by `ID-43`/`ID-44` but is not in the frame's visible render.** Its label, placeholder, validation and max length are all unauthored, so it ships as a plain optional text input with a translated label. Needs design.
5. **Editing and deleting a Kudos are deliberately absent** — no UPDATE or DELETE policy is created. `Màn Sửa bài viết- edit mode` and `Admin - Review content` are separate commissions, and the Live Board's own pen affordance already links to a `ComingSoon` route.
6. **A suspicious 1006px toolbar width** was measured on one node and is recorded in `reports/design-source-analysis.md` rather than trusted; the modal itself measures 752px wide. The implementer should re-measure rather than propagate it.
