# Worked Example — Expense management SaaS (Mode A, abbreviated)

User prompt: 「経費精算のSaaSを作りたい。社員が経費を申請して、上長が承認する。情報設計をして。」

## 1. 前提・目的
- プロダクト目的: 経費申請〜承認〜精算をオンライン化
- 主要ユーザー: 申請者(社員) / 承認者(上長) / 経理
- ユーザーの主目標: 申請者=早く申請して通す / 承認者=溜めずに捌く / 経理=正確に締める
- ビジネス目標: 処理リードタイム短縮、差し戻し削減
- 設計課題: 3ロールで必要情報が異なる → ロール別IA
- 前提・仮定: Web(レスポンシブ), MVP, 多通貨は対象外と仮定

## 2. コンテンツ & タスク整理
| User task | Intent | Information needed | Main action | Success state |
|---|---|---|---|---|
| 経費を申請 | 立替を回収 | 金額/日付/科目/領収書 | 申請送信 | 承認待ちに表示 |
| 申請を承認 | 妥当性確認 | 申請内容/予算/規程 | 承認 or 差戻 | ステータス更新 |
| 精算を締める | 支払処理 | 承認済一覧/振込先 | 精算確定 | 支払済 |

## 3. 情報グルーピング & 命名
- スキーム: ロール別(audience) を一次ナビ、内部はオブジェクト別(申請=Expense)
- グループ: 申請 / 承認 / 精算 / 設定
- 命名メモ: 「申請」「承認」は社内語そのまま採用。"ワークフロー"等の抽象語は不使用。

## 4. ナビゲーション設計
- モデル: ロールでタブを出し分け（ハイブリッド階層）
- グローバル: ダッシュボード / 申請 / 承認(承認者のみ) / 精算(経理のみ) / 設定
- 深さ: 各Must画面まで ≤ 2 階層

## 5. サイトマップ
```text
Expense SaaS
├── ダッシュボード（自分の状態サマリ）
├── 申請
│   ├── 申請一覧
│   ├── 新規申請
│   └── 申請詳細
├── 承認（承認者）
│   ├── 承認待ち一覧
│   └── 承認詳細
├── 精算（経理）
│   ├── 承認済一覧
│   └── 精算確定
└── 設定（科目・承認ルート・ユーザー）
```

## 6. 画面一覧
| Screen | Role | Key content | Primary action | Priority |
|---|---|---|---|---|
| ダッシュボード | inform | 自分の申請状況/要対応件数 | 該当へ遷移 | Must |
| 新規申請 | input | 金額/日付/科目/領収書 | 申請送信 | Must |
| 申請一覧 | manage | 自分の申請+ステータス | 絞り込み/詳細 | Must |
| 承認待ち一覧 | decide | 未処理申請 | 一括/個別承認 | Must |
| 承認詳細 | decide | 明細/規程/履歴 | 承認 or 差戻 | Must |
| 精算確定 | complete | 承認済+振込先 | 確定 | Should |
| 設定 | manage | 科目/ルート/権限 | 編集 | Should |

## 7. 画面遷移
```text
ログイン
→ ダッシュボード（要対応があれば誘導）
→ 新規申請 → 申請送信
  ├─ 必須未入力 → エラー表示 → 再入力
  └─ OK → 承認待ちへ
→ (承認者) 承認待ち一覧 → 承認詳細
  ├─ 承認 → 精算待ち
  └─ 差戻 → 申請者へ通知 → 申請詳細で修正
→ (経理) 精算確定 → 完了
```

## 8. 主要画面の情報優先度
**新規申請** — input:
1. 金額・科目・日付（精算に必須）
2. 領収書添付・メモ
3. プロジェクト/タグ等の任意項目
States: empty(初期) / error(検証) / success(送信完了)

**承認詳細** — decide:
1. 申請金額と科目の妥当性、規程違反フラグ
2. 領収書プレビュー、申請者コメント
3. 過去の同種申請履歴
States: loading / error / success(承認済)

## 10. レビュー結果
- 1画面1役割: OK / 深さ≤3: OK / 空・エラー状態: 主要画面で定義済
- 残課題: 多通貨・経費規程の自動チェックはMVP範囲外（Could）
