# ADR-0004 — Feature-spec audience split: 2-file (functional/technical), single-source codes

**Status:** Accepted (v27.0.0)
**Supersedes:** none
**Cites:** ADR-0003
**Date:** 2026-08-17

---

## Context

A BA or QA reader opening a `docs/features/F###/` directory could not answer "what does this
feature do / how does it behave / what does the screen show" without reading pseudocode,
`file:line` citations, and HTTP verbs — the exact tokens a dev/QA/SA reader needs and a BA/QA
reader does not. Density measurement on the pre-v27 corpus found roughly **10 lines per
business rule** where the plan's acceptance bar calls for **≤2** — the detail a BA needs was
present, but buried inside dev-formatted prose rather than stated as a plain one-liner.

### The genealogy — this is the third link in a chain, and the second link's failure is the lesson

1. **Plan `260419-2037`** rewrote a single `feature-spec-template.md`, user-journey-first —
   the first attempt to make the feature spec readable by a non-developer.
2. **Commit `ce4c6db6`** split that single file into **4 audience files**:
   `business-context.md` (plain-language why/who/what), `screens.md` (screen list + user
   journey), `edge-cases.md` (scenario table), and `technical-spec.md` (the dev/QA/SA detail —
   FR/BR/SM/ALG/INT/SC codes, pseudocode, citations).
3. **v27 (this release)** consolidates back to **2** files, split by **audience** —
   `functional-spec.md` (BA/QA) and `technical-spec.md` (Dev/QA/SA) — with every code stated
   once and implemented once.

**Why (b) failed, stated plainly:** splitting by *document type* is not the same operation as
splitting by *reader*. `business-context.md`/`screens.md`/`edge-cases.md` ended up shallow —
each covering only a narrow slice of what a BA actually needs (why, screens, edge cases were
scattered across three files with no single entry point) — while `technical-spec.md` kept
every code declaration (FR/BR/SM/DEC) in dev-formatted prose, because nothing forced the plain
statement of a rule to live anywhere else. A BA/QA reader still had to open the dev file to
find out what a business rule actually said, defeating the split's own purpose. The diagnosis
is a **detail↔audience inversion**: the axis that was split (document type: context vs.
screens vs. edge-cases vs. everything-else) was orthogonal to the axis that needed splitting
(reader: BA/QA vs. Dev/QA/SA). The fix is to split by reader, with the code STATED once on the
BA/QA side and IMPLEMENTED once on the Dev/QA/SA side — never duplicated, never left only on
the technical side.

## Decision

### 2-file audience split, code-as-anchor, no derived view

Per feature, exactly two files:

- **`functional-spec.md`** (BA/QA audience) — 10 numbered H2 sections: Overview, Open
  Decisions, Requirements, Business Rules, Screens, User Stories, Scenarios, Edge Cases, Edge
  Behaviours to Verify, Configuration. Every `FR-###`/`BR-###`/`SM-###`/`DEC-###` code is
  **stated** here as one plain-language line (≤2 lines/rule, hard budget). No class names,
  `file:line`, HTTP verbs, or pseudocode outside fenced blocks (`FORBIDDEN OUTSIDE FENCED CODE
  BLOCKS` contract) — an inversion of the old `business-context.md` rule, which forbade the
  codes themselves; here the codes are expected, the technical detail is what's forbidden.
- **`technical-spec.md`** (Dev/QA/SA audience) — the same codes are **implemented**: endpoint/
  handler, `Source:` citation, pseudocode, state machines, algorithms, integrations. It never
  restates the plain-language sentence; it cites the code and points back to
  `functional-spec.md § N`.

This is **ADR-0003's single-source principle, applied to the audience axis**: ADR-0003 ruled
that a component's docs live at one language-resolved path with no derived view; this ADR rules
that a feature's codes are declared in exactly one file (`functional-spec.md`) and implemented
in exactly one file (`technical-spec.md`) — neither is a regenerated projection of the other,
and neither may restate the other's content. `## Artifact References` cross-links them; there
is no third, merged, or derived file.

### Consequences elsewhere in the pipeline

- **A1 confidence-report basis change:** `functional-spec.md` is excluded from the A1
  citation-coverage denominator — it is prose-driven by design (plain sentences, not
  citations), so counting it would misread deliberate audience design as a coverage gap. The
  citation-bearing half of the pair, `technical-spec.md`, remains fully in scope.
- **Translation Rule 1a:** a line is skeleton (byte-identical across languages) when it is a
  code token plus surrounding parentheses/braces (e.g. `(BR-001)`); it is prose (translated)
  when it is a sentence. This distinguishes `functional-spec.md`'s trailing-tag code lines from
  its plain-language sentences under the existing skeleton-identity translation gate.
- **`business-rules.md` removal:** `docs/system/business-rules.md` is deleted; its per-rule
  As-Is/To-Be content is absorbed into `docs/generated/behavior-logic.md`, which now owns both
  the BL### inventory and the folded-in rule content. Every artifact that used to cite
  `business-rules.md` cites `behavior-logic.md` in its place.
- **Screen-spec checklist 4→2 rule merge:** the screen-spec verification checklist's rules 9,
  10, 30, and 31 merge into two — `screen.layout_sketch_missing` and
  `screen.layout_regions_missing` (both `critical`) — mirroring the same reader-split logic:
  the BA-facing layout sketch and the dev-facing layout regions are two things, not four.

## Rejected alternative — priced, not assumed (H-SC3)

The sealed decision log recorded the *choice* (migrate existing content, apply an LLM
compaction pass) but not its *trade-off* against the alternative. Both sides, priced:

**Regenerate** (full re-run of `--feature-specs` against the new 2-file templates):
- **For:** reuses the existing, tested wave pipeline end to end; produces new-template density
  (≤2 lines/rule) for free, with no new composition code to write or maintain.
- **Against:** re-derives every feature from source on every migrated repo — re-running the
  full extraction wave for features that have not changed. Any post-generation human edit made
  to the v26 docs (a corrected business rule, a clarified edge case) is **lost** on
  regeneration; the only protection available is the hand-edit probe, and its only response is
  to **skip** the feature entirely, leaving it un-migrated rather than preserving the edit.

**Migrate** (chosen — `migrate_feature_audience_split.py`, Mode A):
- **For:** preserves the existing generated content and any edits folded into it — a
  deterministic content move (parse the 4 v26 files, reassemble into the 10 fixed
  `functional-spec.md` sections + a reshaped `technical-spec.md`), not a source re-read. Where a
  human edit exists, it survives the migration.
- **Against:** costs one-time composition logic (`_audience_split_compose_a_lib.py` +
  `_audience_split_parse_v26_lib.py` + `_audience_split_parse_old_blocks_lib.py` +
  `_audience_split_render_func_sections_lib.py`) plus an optional LLM prose-compaction pass to
  bring inherited content down to the new density bar, both scoped and gated by invariants
  I1–I6 (below).

The user chose migrate with this cost explicitly in view — recorded here so the trade-off, not
just the outcome, survives for the next maintainer.

## The migration-safety deviation (Phase 06, deliberate — do not "fix" it)

`migrate_feature_audience_split.py` is **deliberately unlike** the repo's other five
`migrate-*.py` scripts. The other five migrate in place with no staging directory, no
`--dry-run`, and no retained backup — their safety rests on idempotency alone. This script does
not, because **the v15 in-place MOVE design caused real data loss** (see
`docs/journals/` and the `rebuild-spec-perlang-aggregate-layout-v15` history) when a
data-owning migration was allowed to overwrite its only copy of the source with no way back.
Never again: this script stages, validates, and only then swaps, with a backup retained.

The full machinery, and the invariant each piece answers to:

- **I1 — the sentinel is the sole source of migration state.** No code path infers "already
  migrated" from partial file presence; a crash before the sentinel write means the run resumes,
  never silently no-ops on a half-done directory.
- **I2 — no live source is ever overwritten.** `technical-spec.md` is both an input and an
  output of Mode A; the write path is temp-file-in-real-dir → `os.replace()`, with the pre-swap
  content retained as `technical-spec.md.pre-swap-backup` so a killed mid-swap run has a byte-
  identical restore path via `--rollback`.
- **I3 — the hand-edit probe is fail-closed.** `authored_by:` absence, no git trail (three
  separate untracked/no-`.git`/no-git-binary cases), and `doc_lock: user` all resolve to
  `hand-edited`, never to a default "clean" assumption — an absent signal must never be read as
  permission to proceed.
- **I4 — the verdict gates composition, not just deletion.** A `hand-edited` verdict removes
  that feature's content from the LLM compaction pass's input entirely, not merely from the
  final delete step — a locked file is never fed to the pass at all.
- **I5 — one lock for the whole run, including the LLM pass.** A single lock wraps everything
  from the shape/hand-edit probe through the sentinel write, so two concurrent invocations
  cannot race the staging directory.
- **I6 — unrecognized input shapes are refused, never mangled.** Recognized: v26 4-file
  (migrate) and v27 2-file (no-op via I1's sentinel). Anything else — a pre-v26 single
  `spec.md`, a partially restructured directory — REFUSES with a non-zero exit and zero bytes
  written, rather than guessing a shape and producing a mangled result.

Also deliberately unchanged from `migrate_docs_layout.py`, and **copied as-is, not "fixed"**:
the **POSIX lock file is left on disk** after a run, and the **reverse-index is invalidated
before the sentinel is written**. Both look like bugs in isolation; both are intentional —
removing the lock file introduces a flock/unlink race, and reordering the sentinel ahead of
the index invalidation risks a stale index surviving a crash between the two writes. A
maintainer reading only this ADR should not "re-align" `migrate_feature_audience_split.py`
with the other five scripts' simpler, no-staging model — that simpler model is exactly what the
v15 incident ruled out for any migration that owns data with no other copy.

**Scope note:** `--dry-run` previews Mode A (feature merge) only; Mode B (business-rules fold)
and Mode C (screen-spec reorder) have no dedicated `--dry-run` preview. Modes B and C also have
no dedicated `--rollback` path — a partial run leaves its pre-swap backup under
`docs/.migrate-v27/` for manual recovery; Mode A's `--rollback` is unaffected. Mode A assumes
the source v26 doc is internally self-consistent (every referenced code has a declaring row
somewhere) and emits the bare `SCR###` code (no slug suffix) in its composed Screens table —
`validate_feature_screen_link.py`'s prefix-only match still resolves it.

## Amendment (v27.1.0) — legacy-corpus provenance

**Status:** Accepted · **Date:** 2026-08-17

### Context

`_audience_split_probe_lib.py`'s hand-edit probe treated `authored_by:` frontmatter as its
primary origin signal (I3, above). That signal is written only by takumi's promote path
(`references/spec-authoring-contract.md`) — **rebuild-spec's own generator never emitted it**,
neither for the original 4-file v26 layout nor anywhere in `feature-spec-researcher-contract.md`.
The probe was therefore fail-closed against its own producer: every rebuild-spec-generated v26
corpus resolved `HAND_EDITED` by construction, not because a human had touched it.

Measured on the real sharetribe corpus (66 features, 182 screens, 1 `business-rules.md`, zero
YAML frontmatter anywhere, generated 2026-06-04): **249/249 units** — every feature, every
screen, and the business-rules file — resolved `skipped-hand-edited`, exit 0, with the run
sentinel written anyway. A migration that cannot migrate a single real, unedited corpus is a
producer/consumer contract gap, not a corpus quirk: the fixture suite stayed green throughout
because `_write_v26_feature()`'s test helper hard-defaulted `tech_frontmatter="authored_by:
rebuild-spec"`, handing every probe test a signal no real corpus ever emits.

### Decision

Provenance splits into two signals at different granularity, per phase-00's design consequence:

- **Origin, per UNIT (new):** at least one file in the unit carries a recognized *generator*
  marker — `<!-- Contract: … -->` at line 1, or a `**Generated**: DATE` line, in addition to the
  existing `authored_by:` frontmatter signal. On the sharetribe corpus `**Generated**: DATE` had
  full coverage (66/66 `technical-spec.md` files) and is therefore load-bearing; `<!-- Contract:
  … -->` covered 41/66. No file in the unit carries any of the three → `HAND_EDITED`, preserving
  the fail-closed spirit of I3.
- **Integrity, per FILE (unchanged):** `doc_lock: user`, a foreign `authored_by:`, a missing git
  trail, or a working-tree diff against HEAD still resolve that file — and therefore the whole
  unit — to `HAND_EDITED`. Origin says "a generator wrote this directory"; the git trail says "no
  byte has moved since." Both remain required; unit-level origin does not relax per-file
  integrity.
- **Going forward:** P07 makes rebuild-spec's own templates and researcher contracts emit
  `authored_by: rebuild-spec` at generation time, the same signal takumi's promote path already
  writes. A corpus migrated once under this amendment carries `authored_by:` on both output files
  and never needs the legacy-marker fallback again — the fallback is a bridge for pre-27.1.0
  corpora, not a permanent second path.

### Consequences, stated honestly

- **`**Generated**: DATE` is human-forgeable.** The exposure class is **unchanged** by this
  amendment — `authored_by:` was already equally forgeable (a human who hand-edits a generated
  file can leave either marker in place today). `doc_lock: user` remains the documented mechanism
  for marking a hand-authored file inside an otherwise-generated tree, and `--reviewed` sample
  review (≥10% of the run's eligible features, minimum 3) remains the single human gate before
  any original is deleted. `CLEAN_LEGACY` (the verdict a marker-backed unit receives) does not
  itself unlock deletion — it only lets the run proceed past the probe.
- **Unit-level origin means one marker-bearing file vouches for the *origin* of its markerless
  siblings** (e.g. `technical-spec.md`'s `**Generated**` line vouching for `business-context.md`,
  `screens.md`, `edge-cases.md`, none of which carry any marker at all — see phase-00's marker
  census). Their *integrity* is still checked individually via the git trail, so no unreviewed
  byte passes on the strength of a sibling's marker.
- **This is a one-time bridge, not a weakening of I3.** A newly-generated v27.1.0+ corpus carries
  `authored_by:` from the start and never depends on the legacy-marker path; the amendment exists
  only so that every corpus generated *before* this fix is reachable at all.
