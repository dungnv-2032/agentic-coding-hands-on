# ADR-0005 — Feature clustering: criteria into W5, and into the critical check that already asked

**Status:** Accepted (v27.4.0)
**Supersedes:** none
**Cites:** ADR-0004
**Date:** 2026-08-20

---

## Context

Two places in the pipeline should carry feature-boundary criteria. Neither did.

**W5 generates the partition** with one instruction: *"Generate FeatureList from all prior
drafts. Template: feature-list-template.md. Schema: references/code-formats.md."* The schema it
points at defines what a valid **single** feature looks like — Clear Flow, Independently
Testable, Agent Implementable. Nothing in it says whether two groups of user stories belong
**together**. `F063` on the pinned corpus — one user story, one screen, **15 background logic
blocks**, unanimously judged over-scoped by three independent labelers — satisfies all three
criteria.

**W5.6 check #8 already asked the question, at `critical`, with no rule behind it:** *"Grouping
coherence: do F-code assignments reflect logical feature boundaries? No F### should aggregate
unrelated concerns → critical if clearly mixed concerns."* Right question, no definition of
"unrelated", and no evidence to apply. An LLM reviewer meeting that with no rule passes
everything.

Four designs were attempted against this gap over two plans. Three died. This ADR records all
four, their causes of death, and the findings that outlive them — because two of those deaths
were caused by measurement errors that would otherwise be repeated.

---

## Decision

### The criteria are written once, and both the generator and the existing check point at it

`references/code-formats.md` gains `### Feature Clustering Rule (authority)`, following the
convention `### Capability-Level Intent (authority)` established: *"every other document that
touches this rule links here by heading name; none restates it."*

- Both W5 clustering entry points reference it by heading — the single-task branch, and the
  shard branch's **grouping-once** step (the fan-out expand step correctly gets nothing: it
  expands details for F### already assigned, it does not cluster).
- Check #8 references it by heading. **Its severity is unchanged (`critical`).**
- `build_session_context.py`'s always-read pointer for `code-formats.md` — previously described
  as *"— code schemas"* — names the clustering rule too, so an agent reading the file for
  *schemas* is told it also carries a prose rule.

**No new check, wave, schema, or template.** The prompt surface moves by **19 lines** across four
files — the authority block (14), one reference line per W5 branch (2), one for check #8, one for the
session-context pointer — and one behavioural line restores W5.6's missing halt threshold (below).

**The footprint, counted honestly.** An earlier framing of this work claimed *"about 20 lines added,
710 removed"*; computed from `git diff` against the pre-change base, neither half holds. The 710 lines
of retired v3 code were **never tracked**, so nothing was removed from the shipped kit — they are gone
from the working tree and preserved in history, which is the actual benefit, not a line-count
reduction. And the same framing budgeted *"1 new tracked file"* while the label fixture, the scorer and
its test — roughly 2,000 lines this ADR depends on for every figure it cites — were untracked and had
to be committed, or the citations below would have been unfalsifiable. Real net on `claude/`:
**+2268 / −3 across 14 files**, of which 19 lines are the prompt change the budget was actually
guarding. The prior draft of this work was criticized for a budget that excluded a test file and a
one-off script; its replacement excluded a 2,000-line fixture and counted a removal that never
existed. Recorded because an anti-bloat claim that cannot survive `git diff` is worse than none.

### The one behavioural change: W5.6 could not actually halt

Giving check #8 criteria is pointless if its findings cannot stop anything, and they could not.
W5.6's frontmatter contract said `false = halt` but never that a critical *requires*
`passed: false`, and the orchestrator throws only on `passed === false` — it reads `issues` merely to
interpolate into the error message. A reviewer finding a check-#8 critical could report `issues: 1,
passed: true` and proceed to FS.1, with the console printing `[INFO] W5.6 passed (issues: 1,
warnings: 0)` — a log line asserting a pass while reporting a critical.

**W4.6, the sibling gate one wave earlier, already carried the missing instruction** (*"Halt
threshold: passed=false only when issues > 0"*). W5.6 never got it. That line is now copied across,
naming which checks count as criticals. It adds no check and no gate — it makes the existing critical
gate's output contract consistent with its own sibling — but it does change **when W5.6 halts**, so it
is named as a behavioural change rather than folded into the documentation edit.

The general lesson, which is the same shape as findings 4 and 5: **a gate's severity label is not its
teeth.** A check can be `critical`, be read by an orchestrator that halts on failure, and still never
halt, because the step that converts a finding into the halt signal was left to an LLM's discretion
with no instruction. Naming a check critical is cheap; wiring its finding to the halt is the part that
gets forgotten.

### Why this is a MAJOR bump despite adding no check

Check #8's severity is untouched. But today it has no criteria and passes everything; with
criteria it fails an `F063`-shaped feature. That is this skill's own major trigger, stated in
`CHANGELOG.md`'s version policy: *"a previously-passing document can now fail."* **Severity is
not the trigger — outcome is.** An earlier draft of this work argued minor on the grounds that
severity was unchanged; that reasoning was wrong and is corrected here rather than defended.

## The four designs and their causes of death

| # | Design | Cause of death |
|---|--------|----------------|
| 1 | Declare a capability partition at W5 + `--migrate split-feature`; BREAKING 28.0.0, 34h | The gate never sat on the path FS.1 dispatches from. The § 2 pre-seed targeted a migrate-only file whose goal state was unreachable. The split step was not implementable at the estimate given |
| 2 | Deterministic counting rule `#CAP>=2 AND row(US>=3, SCR>=1)` | **60% precision / 30% recall** against the labels. Its earlier "100%" was agreement with `cap.promote_candidate` — **another unvalidated rule it had been derived from** |
| 3 | Screen + LLM judge + two-tier gate, 17h | Judge scored **100% precision / 30% recall on 3 fires** — Wilson 95% CI **[43.8%, 100%]**, an interval wide enough to be uninformative. Its rubric was reverse-engineered from the labelers' own rationales for the same 18 features, then scored on those same 18. The judge added **no recall** over the deterministic screen it was meant to improve on |
| 4 | **Criteria into W5 and into check #8** *(accepted — this ADR)* | — |

### Design 2's fatal detail, stated so it is not repeated

The counting rule was calibrated against `cap.promote_candidate` and scored 100% agreement.
`cap.promote_candidate` had itself never been validated against human labels. The 100% measured
**how faithfully one unvalidated rule reproduced another** — it contained no information about
correctness. Against real labels the same rule scored 60%/30%.

### Design 3's fatal detail, stated so it is not repeated

The judge rubric was authored **from** the labelers' written rationales for the 18 labeled
features, then evaluated **on** those same 18 features. That is scoring a rubric on its own
answer key. The resulting figure describes memorization, not generalization. Three fires is also
too few to distinguish a good judge from a lucky one — the Wilson interval says so directly.

## Findings that outlive all four designs

**1. Capability count is not the over-scope signal.** `F039` — CAP=7 — was **unanimous KEEP**.
`F063` — CAP=8 — was **unanimous SPLIT**. The *axis* of grouping decides, not the count. Any
future design that reaches for a CAP threshold should read this row first.

**2. The best-scoring counting rules cannot run where the decision is made.** `CAP>=5 OR US>=5`
scores 77% precision / 100% recall — and is **unusable at W5/W5.6**, because § 2 (and therefore
CAP) does not exist until FS.1, a later wave. Every CAP-bearing rule shares this defect. The
rules that are usable pre-FS.1 score materially worse. This is a structural constraint on the
problem, not a tuning failure.

**3. The discriminators are qualitative, and readable from `feature-list.md` alone** — no later
artifact required: grouping by implementation mechanism, two different actors, a separate data
model per sub-group, already-separate route namespaces, storyless screens.

**4. Never calibrate against another unvalidated rule.** (Design 2.)

**5. Never author a rubric from the answer key, then score it on that same set.** (Design 3.)

## The criteria, and exactly what was measured

The shipped rule groups user stories by **primary business intent** — never by artifact volume,
technical layer, or implementation mechanism. It carries no numeric threshold, by construction:
a rule that forbids count-based reasoning must not contain a count.

**Measured basis, inline and complete:**

- The judgment form of the criteria scored **86% precision / 60% recall** across **3 independent
  runs**, against **30% recall** for the prior rubric on the same set.
- **n=18**, and the sample is **deliberately enriched** — the 18 features were chosen across
  suspicion bands (flagged / near-miss / high-CAP / background / small control). The sample's
  56% SPLIT rate is **the sample's**, and must never be read as the corpus rate.
- **Fleiss kappa = 0.481** (moderate). These labels are not a gold standard.
- The rules were searched against these same labels, so **every figure above is an upper bound.**
- **`F020` and `F046` were never human-adjudicated.** Both were 2–1 majority votes that stand as
  ground truth on the strength of the majority alone. Five features (`F001`, `F006`, `F015`,
  `F032`, `F058`) were user-adjudicated; none of those adjudications overturned the majority.
- **The misfiled-story bullet is UNMEASURED.** It was the trial's recommendation for its single
  false positive (`F015`) and was never itself run. It ships **marked unmeasured in the authority
  block itself**, which makes it the first candidate for removal if a future measurement
  implicates it. The distinction ships with the rule rather than being smoothed over.

**What this work does not claim.** No behavioural claim is made about W5's output quality. This
change is proven to give a critical check the rule it never had. Whether an instruction line
changes a one-pass global clustering task over roughly **11,400 lines** of input drafts is an
open question — see the follow-up below. The trial measured **small-context, single-feature**
judgment; W5 does **large-context, global** construction. No evidence carries from the first to
the second, and that gap is accepted unmitigated rather than implied away.

## Follow-up work, recorded so it is not lost

### The A/B measurement — deferred, with its harness defect named

The measurement that would settle the open question above was designed and found unrunnable
before it was run. **The defect: the harness staged its six input artifacts outside the repo for
isolation, then instructed arm B to read a repo file that was never staged.** Arm B could not
reach the authority text, would have behaved identically to arm A, and would have produced a
null result **caused by the harness** — which the plan would then have had to interpret as
evidence about the rule.

A correct next attempt needs all three of:

1. the authority text **staged for arm B**, inside the isolated input set;
2. **≥3 runs per arm** (design 3's 3-fire Wilson interval shows what fewer buys);
3. a **decision boundary named before the run**, not chosen after seeing the output.

It is deferred, not cancelled. A gate design retired on the strength of a missing measurement can
be revived by that measurement as easily as retired by it.

### Incremental carry-forward — a known limitation, not fixed here

W5 and W5.6 both skip when `w5_reran === false`. A `feature-list.md` generated **before** this
rule shipped carries forward through incremental runs and is never re-checked against it, with no
freshness stamp to mark that it predates the criteria. Adding a version stamp to generated
artifacts is its own change with its own blast radius; it is not smuggled in behind a
documentation edit.

### The headline figure has no tracked reproduction path

`scripts/measure_feature_split_rules.py` reproduces every **counting-rule** figure in this ADR from
the tracked fixture — design 2's 60%/30%, the 77%/100% pre-FS.1 row, `n=18`, kappa 0.481, and the
`F039`/`F063` labels. It cannot reproduce **86% / 60%**: that figure came from the *judgment* form of
the criteria, which is an LLM run, not a scoreable rule, and its per-run outputs live under
gitignored `plans/`. So the number driving this change's version bump is disclosed with every caveat
but **auditable only on trust** from anything committed here. "No tracked file cites an unfalsifiable
path" and "the figure itself is falsifiable" are different properties; only the first is enforced.
Landing the per-run judgment outputs as a tracked artifact, the way `labels.json` already is, is the
fix — recorded as follow-up rather than claimed as done.

### Unprovable from the pinned corpus

Whether check #8 ever fired on `F063` cannot be established — the plan-directory artifacts from
that run were not preserved. The question is recorded as unanswerable rather than guessed at.

## Addendum (v27.6.0) — the multi-outcome-name bullet, and why it directs rather than decides

Added from a field report, not a measurement. A user asked why a 33-feature corpus full of
`A & B` feature names passed W5.6 — *"Tại Feature lại có dạng A&B mà vẫn pass?"*

**Why it passed, and all three reasons are working as designed.** No deterministic validator ever
reads a feature's *name*: the only name rule is `SLUG_RE = ^F\d{3}_[A-Za-z0-9]+$`, and
`_slug_lib.derive_slug()` does `.replace("&", " And ")`, so the conjunction is laundered into an
ordinary word (`F001_MarketplaceDashboardAndGeneralConfig`) before anything downstream sees it.
Check #6 forbids only a banned generic noun *standalone* — it tests for a VAGUE name, not a BROAD
one — so the reviewer reported honestly that *"every F### name pairs a generic noun with a specific
qualifier"*. Check #8 is the right check and is `critical`, but it judges US membership, and nothing
in the authority told it that a name declaring two outcomes is itself evidence to examine.

**Why the obvious fix was refused.** A deterministic conjunction rule would flag **27 of 33** names
on that corpus, of which the reviewer's semantic pass found **2** real defects (`F013`, split
required; `F031`, no identifiable trigger) — roughly **7% precision**, and 25 recurring warnings that
would drown the real ones. `Direct Messaging & Inbox`, `Authentication (Login & Password Reset)` and
`Own Listing Creation & Editing` are each one outcome. This is Finding 1 restated in a new costume:
*the axis of grouping decides, not the count*, and a rule that forbids count-based reasoning must not
smuggle one in as syntax.

**What shipped instead.** One authority bullet marked **UNMEASURED**, plus a procedural requirement
in check #8 to ENUMERATE multi-outcome names with a one-line verdict each. The enumeration is the
part that matters: the scan is cheap and name-shaped, so an unenumerated name reads as unexamined,
while the conjunction still carries no verdict on its own. The bullet also states the converse the
7% figure implies — a single-outcome name earns no free pass either.

**The honest signal strength.** Both features the reviewer *did* flag had conjunction names. So the
conjunction is a good attention signal and a poor verdict signal, which is precisely the shape of
thing that belongs in a judgment check's field of view rather than in a gate. n=1 corpus; the
Provenance block names this bullet as unmeasured alongside the misfiled-US one, and it is an equal
first candidate for removal.
