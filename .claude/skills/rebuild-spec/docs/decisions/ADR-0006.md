# ADR-0006 — technical-spec.md: action-first spine, handler-as-identity, deferred diagram criterion

**Status:** Accepted (v27.7.0)
**Supersedes:** none (extends ADR-0004's audience split; the technical half's internal shape changes, the 2-file split does not)
**Cites:** ADR-0004
**Date:** 2026-08-24

---

## Context

ADR-0004 split the feature spec by audience — `functional-spec.md` (BA/QA) states each rule once;
`technical-spec.md` (Dev/QA/SA) implements it once. That split held. What it did not fix: inside
`technical-spec.md`, the layer-first shape (`## 2. Functional → Technical Mapping` keyed on CODE,
`## 3. System Design` keyed on STRUCTURE, `## 4. Technical Behavior by Capability` keyed on
CAPABILITY) gave a reader no single place to answer "when the user clicks this button, what
happens" without assembling the answer from three tables at three different keys.

### The corpus finding that forced the decision, not a taste for a different diagram

Measured on a 43-feature / 430-action corpus (sharetribe, 2026-08-24): the layer-first shape's
`**Applies to:**` free-text field — the only thing standing in for an action→rule binding —
resolved to a specific action only **26%** of the time (93/359 matches). **84% of actions had no
rule attributable to them at all.** This is not a readability complaint; it is a missing binding.
A reader (or a validator) asking "which rules gate this action" had no mechanical way to answer
it for 5 out of 6 actions on this corpus. That number, not the readability argument that opened
the consultation, is why this reshape shipped — see
`plans/reports/brainstorm-260824-1027-technical-spec-action-thread.md` § 10.1 for the full
walk-back: the consultation's own author records that its readability-first framing was corrected
mid-run once the binding gap was measured.

## Decision

### Action-first over layer-first

`technical-spec.md`'s spine changes from CODE/STRUCTURE/CAPABILITY-keyed sections to
ACTION-keyed sections:

- **`## 2. Action Index`** — one row per action: handler, `Method · Path`, the codes it claims,
  the tables it writes, a pointer into § 3. This IS the action→rule binding the layer-first shape
  lacked — every FR/BR/DEC/SM/US code must be claimed by **at least** one row (or the reserved
  cross-cutting `A0` row), checked mechanically, not left to free text. **Corrected post-launch:**
  this originally read "exactly one row" and shipped as `FeatureSpec.action_double_claimed`; the
  Addendum below records why that was wrong and was retired.
- **`## 3. Actions`** — the body, immediately after the index (not buried behind a "system
  design" wall). One capability bucket per row in the twin `functional-spec.md § 2`, each
  holding one block per action. Every block uses the SAME labelled rung set: **Who → FE →
  Request → BE → Rule → Result → Source**. An absent rung is omitted, never stubbed.
- **`## 4. Shared Foundation`** — what used to be § 3 System Design, demoted to an appendix.
  Components, data model, state machines, shared rules (see the three-bin decision below),
  algorithms & integrations, configuration. Actions in § 3 point here; nothing here repeats a
  fact a single action's rung already stated.

`## 5. Verification & Technical Notes` and the two unnumbered literal H2s after it
(`## Source Walkthrough`, `## DB Impact per Event`) are unchanged.

### D2 — handler-as-identity, not `METHOD PATH`

The § 2 Action Index keys each row on `` `Class#method` ``, never on `METHOD PATH` alone. Two
reasons, both structural, not stylistic: the same path can back two different actions (e.g. two
member routes sharing `/:id`), and a background action (queue/job/cron) has no HTTP path at all.
`` `METHOD PATH` `` is kept as a last-resort fallback for a genuinely unparseable handler, and
that fallback is itself instrumented (`FeatureSpec.action_key_not_handler`, warning) — reaching
for it is a signal to re-read the code, not a shortcut.

### The three-bin rule for shared rules (§ 4.4)

A rule's placement is decided by **how many named actions use it, counted**:

- **Bin 1** (used by exactly one action) — inline in that action's Rule rung, full statement +
  citation. Not duplicated.
- **Bin 2** (used by ≥2 named actions) — one full block in § 4.4, tagged `Used in: A2, A3`; each
  using action carries a short reference line only.
- **Bin 3** (belongs to no single action — a controller-wide gate, for example) — also in § 4.4,
  claimed by the `A0` row, carrying an explicit cross-cutting label.

Bin 3 is the bin the corpus argues for as a THIRD bin rather than a Bin-2 special case: without a
dedicated home, a rule that gates every action on a controller gets stuffed into whichever action
happens to need a home for it, which corrupts the exact binding § 2 exists to create — the rule
now reads as belonging to one action when it actually gates all of them.

### The deferred criterion: diagrams gate on (b) OR (c), not (a)

A `sequenceDiagram` is added to an action's block when it satisfies **≥1** of three candidate
criteria: (a) the action has ≥2 BR/DEC, (b) it writes ≥2 tables, (c) it is a background/async-step
action. Measured on the same corpus: (a) fires on only **4.4%** of actions. Shipping a criterion
this thin, before the action→rule binding it depends on (§ 2) has run on a real corpus at scale,
risks calibrating a diagram threshold against noise. **(b) and (c) ship at launch; (a) is
deferred** until § 2 has been exercised on more corpora and the base rate can be re-measured, not
guessed. A future re-measurement may re-add it, lower it, or drop it outright — this ADR records
the deferral so the criterion is revisited on evidence, not reintroduced from intuition.

### The removed 400-line ceiling, replaced by a count-based gate

`templates/technical-spec-template.md`'s prior `LARGE OUTPUT NOTE` ("if this file exceeds 400
lines, signal to orchestrator for chunked review") is removed outright, per the user's explicit
ask. It served two jobs at once — a file-size opinion (drop it) and an agent output-budget guard
(re-based, not dropped). The replacement, `scripts/decide_action_chunking.py`, chunks generation
by CAPABILITY when a feature's § 2 Action Index row count is `>= REBUILD_ACTION_CHUNK_THRESHOLD`
(default 15) **AND** the twin functional-spec has `>= 2` capabilities — never on a line count.
Corpus check on the slice axis: every feature with ≥15 actions on the measured corpus has ≥5
capabilities (5, 5, 5, 6, 7, 7, 8 across the 7 qualifying features), while every single-capability
feature is small (`F011`: 1 capability, 8 actions) — so "chunk by capability" never meets a
feature it cannot slice. Output stays ONE `technical-spec.md` per feature either way (D6, LOCKED)
— chunking slices generation, never the artifact — reusing the existing fragment/merge mechanism
from `plans/260602-2230-rebuild-spec-chunked-artifact-generation/` rather than inventing a second
one.

**Why a script, not a reference-file rule.** `references/pipeline-feature-specs.md` is a
reference read by the orchestrator LLM, not code. A chunk rule written only there is prose —
"a rule believed to be running," the exact defect class this repo has hit repeatedly (see
`docs/decisions/ADR-0005.md`'s W5.6 finding for the most recent instance). The reference file now
only calls the script and obeys its `{chunk, slices, reason}` JSON; it does not restate the
predicate.

### The `+34%` volume trade, accepted with sharding as the answer, not a contradiction

Measuring the B-v sample against the real v27-shaped original it was derived from (both counting
the same feature, `F011_ListingModeration`, HTML comments and blank lines excluded): **374 → 500
lines, +34%**. This is not the file getting bloated by accident — it is the direct cost of giving
every action the same uniform rung set even when a diagram absorbs some of that action's content.
An earlier draft revision saved 17% by letting diagrams *replace* rungs; the shipped design keeps
the full rung set on every action regardless of whether it also carries a diagram, because a
uniform rung set is what makes the file read as one consistent thread rather than two different
formats depending on which action a reader lands on. That consistency is worth the content, and
it does not contradict the removed line-count ceiling: the ceiling was removed because it offered
no next step once tripped ("signal to orchestrator for chunked review," then nothing), while
`decide_action_chunking.py` gives the file a real answer once it is long — chunk by capability,
merge to one file. The corpus this reshape was measured against already averages **488 lines**
per `technical-spec.md`, peaking at **1128** (`F004_OrderTransactionLifecycle`), with one feature
(`F010_ListingCatalogConfiguration`) resolving **47 actions** — the shard mechanism is not
theoretical headroom, it is answering a condition the corpus already contains today.

### Dropped without replacement: the feature-level Call Hierarchy diagram

The pre-thread `## Source Walkthrough`'s `### Call Hierarchy` diagram (one call chain for the
whole feature) is dropped from the target template. Each action's own `**Source:**` rung in § 3
now carries that action's call chain individually, which is more precise than one diagram
attempting to represent N independent call chains for N actions. `### Call Hierarchy` is not
enforced by any validator (`scripts/scaffold_spec.py` emits it as boilerplate; no check in
`validate_reading_guide_db_impact.py` requires its presence), so this is a template-authoring
decision, not a contract break — a later phase's scaffold update should follow suit.

## Consequences elsewhere in the pipeline

- **§ 5.4 Source References and `## DB Impact per Event` both gain a leading `Action` column.**
  Verified (phase 08 assumption inventory, 2026-08-24): no consumer of either table
  (`derive_confidence_report.py`, `_confidence_report_refresh_lib.py`,
  `validate_source_citations.py`, `build_source_to_fcode.py`,
  `validate_reading_guide_db_impact.py`) parses by column position — the last of those resolves
  its column by header name. Leading position was chosen for reader consistency between the two
  tables, not because a consumer required it.
- **The citation rung form is measured, not assumed.** The Source rung is the one rung with no
  ` · ` separator — `` **Source:** `path:line` `` — because `derive_confidence_report.py`'s
  `CITATION_RE` needs the colon inside the bold markup with plain whitespace after it; the middot
  every other rung uses is fatal to the match. Getting this wrong drops A1 citation coverage
  corpus-wide with no error and no signal — recorded here because the wire-format contract's own
  first draft got it wrong before this was measured against the real regex.
- **`REQUIRED_SYSDESIGN_H3` is deprecated in place, not deleted, by this phase.** Four non-test
  modules still import it (`validate_feature_spec.py`, `scaffold_spec.py`,
  `_feature_sot_structure_lib.py`, `_audience_split_ccl_normalize_lib.py`); deleting it before
  those importers are converted is a `KeyError` in a still-live migrate step, not a cleanup. A
  later phase (blocked by every phase that touches this constant) owns the deletion.
- **`REQUIRED_H2_TECH` stays byte-identical for the same reason** — `_feature_sot_technical_lib.py`
  indexes a `sections` dict keyed by its exact strings; redefining the list in place is a
  `KeyError` in the still-live `feature-sot` migrate step. The new shape lives under its own name,
  `REQUIRED_H2_TECH_THREAD`, until a later phase repoints the exact-order validator.
- **A validator gap, named rather than silently inherited:** `FeatureSpec.dec_blocks_well_formed`
  and `FeatureSpec.dec_lazy_na` check the pre-thread H4 `DEC_BLOCK_RE` shape. Under this reshape,
  `DEC-###` is a table row, which those checks will not match at all — left unfixed, they would
  report a silent pass on a correctly-shaped action-thread file. Recorded in
  `references/verification-checklist-feature-spec.md` as a named follow-up, not fixed in this
  documentation-only phase (it requires a `.py` change).

## Addendum (2026-08-24) — `action_double_claimed` retired: a partition model imposed on a fan-out relation

Phase 11's real-corpus acceptance run (43 features, sharetribe) reported 358 criticals and called
them three systemic composer defects, routing all three back to phase 05 for a fix. Independent
verification on the same corpus found the causation right on two of three and wrong on the third:
**"action double-claimed" (127 instances) was not a composer defect. It was a modelling error in
this ADR's own § 2 decision, coordinator-authored and implemented faithfully.**

**What the rule said.** § 2's Codes column ("every FR/BR/DEC/SM/US code must be claimed by exactly
one row") was copied from `cap.double_claimed` (§ 2 Functional Capabilities), where codes
genuinely partition — each requirement belongs to exactly one capability by construction. The
copy carried the partition assumption into a relation that does not have it.

**Why the assumption fails here.** An action is a *handler*, not a *requirement*. One requirement
routinely fans out to several handlers: an export flow is a request/poll/generate triple: three
actions, one requirement (`FR-203`); an approve/reject pair often shares the same underlying
requirement to change state (`FR-204`/`FR-205` similarly). This is not sloppy modelling of the
input — it is the normal shape of a UI or API surface, and the plan's own hand-authored B-v
reference sample (`plans/260824-1101-technical-spec-bv-sample/technical-spec.md` § 2) demonstrates
it without being asked to: `FR-203` spans A5/A6/A9, `FR-204` spans A2/A7, `FR-205` spans A2/A8.

**Measured, not assumed, before deciding keep/demote/drop.** Migrating the full 43-feature corpus
through the real composer and running the real validator: **127 firings across 31 of 43 features**
(72%). The claim-width distribution:

| Claim width (rows sharing one code) | Count of codes |
|---|---|
| 2 | 108 (85%) |
| 3 | 11 |
| 4 | 2 |
| 5 | 3 |
| 6 | 1 |
| 9 | 1 |
| 10 | 1 |

**Decision: remove outright, not demote to a threshold-gated warning.** A demotion needs a cutoff
that separates "implausible fan-out" from "a feature with a few more handlers." The measured
distribution has none — widths 2 through 10 form one continuous, thinning tail with no gap to cut
at, and 85% sit at the width (2) that is also the single most ordinary shape (a read/write pair,
a poll/generate pair, an approve/reject pair). Picking any threshold above 2 would flag the long
tail's genuinely complex features (`F004_OrderTransactionLifecycle`, 18 double-claimed codes on
its own) while calling that a defect rather than what it is — more handlers touching a shared
requirement on a bigger feature. Picking 2 as the threshold reproduces the original bug exactly.
Any number in between is a guess dressed as a measurement, which is the same failure class this
correction exists to close, not a smaller version of it.

**What stays.** `FeatureSpec.action_unclaimed` is untouched: every declared code must still be
claimed by *at least* one row (or `A0`) — that completeness requirement is the actual binding this
ADR set out to create, and fan-out does not weaken it. Only the exclusivity half was wrong.

**Where this was corrected.** `scripts/validate_feature_spec.py` (`_check_action_thread`, code and
its docstring), `scripts/tests/test_action_index_validation.py` (the check's tests removed, a
retirement block left in their place), `references/feature-spec-researcher-contract.md` and
`references/verification-checklist-feature-spec.md` (all "exactly one" wording naming the Action
Index Codes column corrected to "at least one"), and
`plans/260824-1128-rebuild-spec-action-thread-v27-7/wire-format-contract.md` § 2 itself, the
normative source this ADR and three phases were built from.

**The transferable lesson.** A cardinality rule copied from one section to a structurally similar
but semantically different section is not free — "looks like the same shape" is not "is the same
relation." § 2 Functional Capabilities partitions by construction (every requirement belongs to
one capability); § 2 Action Index does not (one requirement, many handlers is normal). The fix
cost one modelling correction and a corpus measurement; shipping it silently would have meant
every migrated feature above trivial size failing acceptance on a rule that was never true.

## Addendum (2026-08-24) — `diagram_required_missing` gains a fill-pending degradation window

Migrating the full 43-feature corpus through the real composer and running the real validator
(same exercise as the `action_double_claimed` addendum above, this time targeting
`FeatureSpec.diagram_required_missing`): **117 criticals across 28 of 43 features**, on the FIRST
validation pass after `--migrate --only action-thread`, before any researcher ever opens the file.

**Why this is not a composer defect (unlike the addendum above, this one needed no correction to
the rule itself).** `compose_action_thread` is mechanical-only by design (see "Decision" above) —
it cannot author a `sequenceDiagram`; drawing one needs judgment, so it is deferred to the
researcher fill pass, the same pass that resolves any rule the composer could not bind (marked
`[UNVERIFIED]`). Every one of the 117 findings is therefore real (an over-threshold action
genuinely lacks a diagram) but premature (the pass that would supply it has not run) — "migrate
then validate" was red by construction, making the plan's own success criterion #2 unreachable by
migration alone.

**The signal chosen, and why it is honest.** Three candidates were on the table: the `[UNVERIFIED]`
tag the composer already emits for unresolved rules; `ThreadComposeResult.needs_llm_fill`, a
runtime return value that does not survive past the migrate process exiting (unusable by a later,
separate `validate` invocation); and "does the file carry any mermaid fence at all," which is not
scoped correctly (a file may have 1 of 3 required diagrams). `[UNVERIFIED]` was chosen: it is
artifact-derived (AD-1, survives on disk, same convention as `_TECH_PRE_THREAD_SENTINEL`), it is
the SAME tag `_doc_migration_action_thread_step_lib` already counts into the `action-thread`
migrate step's own rollback sidecar (not a new marker invented for this), and — measured, not
assumed — 0 of the 28 features that fire `diagram_required_missing` on this corpus carry zero
`[UNVERIFIED]` markers. Per this ADR's own C11 finding (every DEC block is unresolved by
construction), a feature with no DEC blocks and every BR fully resolved could in principle carry
none while still pre-fill; no such feature exists in the measured corpus, and if one arises later
it is, correctly, treated as already past the window — it has nothing left for a fill pass to
resolve.

**Decision: degrade `diagram_required_missing` to `warning` while `[UNVERIFIED]` is present;
revert to hard `critical` once it is not.** Implemented via `_thread_sev_msg` (the SAME D4
degradation helper `_check_action_thread`'s `is_pre_thread` window already uses, extended with an
optional `reason=` for the message suffix — not a second mechanism), gated on
`_action_thread_diagram_lib.is_fill_pending`. Scoped to this one rule_id only: the other 4 in the
same check function (`rule_bin_misplaced`, `crosscutting_unlabelled`, `diagram_cites_file_line`,
`diagram_over_cap`) and the 5 action-thread codes in the sibling function are untouched — this is
not a second `tech_sections_pre_sot`-style whole-section mute.

**Before/after, same corpus, every other rule_id unchanged:**

| rule_id | severity | count (before) | count (after) |
|---|---|---|---|
| `FeatureSpec.diagram_required_missing` | critical → **warning** | 117 | 117 |
| `FeatureSpec.action_unclaimed` | critical | 1 | 1 |
| `FeatureSpec.crosscutting_unlabelled` | warning | 23 | 23 |
| `FeatureSpec.dec_lazy_na` | warning | 5 | 5 |
| `FeatureSpec.diagram_over_cap` | warning | 4 | 4 |
| `FeatureSpec.f_code_format` | critical | 43 | 43 |
| `FeatureSpec.pseudocode_length` | warning | 1 | 1 |

**What was NOT weakened.** Once the researcher fill pass resolves every rule (the file's
`[UNVERIFIED]` count reaches 0), a still-missing required diagram reverts to a hard `critical` —
proven by `TestDiagramRequiredMissingFillPendingWindow.test_critical_once_fill_is_resolved` and by
`TestF953MissingDiagram` against F011's real corpus shape. This is a promotion path (warning while
legitimately mid-pipeline, critical once it is not), never a permanent relaxation — the eighth gate
this build's own preflight found silently dead was exactly the failure mode this addendum is
careful not to add a ninth instance of.

**Where this was implemented.** `scripts/_action_thread_diagram_lib.py` (`is_fill_pending`, the
`_UNVERIFIED_MARKER` literal duplicated from `_doc_migration_action_thread_step_lib.py` rather than
imported — importing would invert the read-only validator's dependency direction onto a mutating
migrate-step registry module), `scripts/validate_feature_spec.py` (`_thread_sev_msg`'s new
`reason=` parameter, `_check_rule_bins_and_diagrams`'s `diagram_required_missing` branch),
`scripts/tests/test_action_thread_diagrams.py`,
`scripts/tests/test_action_thread_shapes_corpus.py` (`F953_MissingDiagram`'s expectation updated —
it is a real corpus file that carries 3 `[UNVERIFIED]` markers, so it now correctly demonstrates
the window rather than a pre-window critical), and
`references/verification-checklist-feature-spec.md` / `references/feature-spec-researcher-contract.md`
(the window documented, plus an ordering note: resolving every rule without also drawing every
now-required diagram turns this same warning back into a critical).

## Addendum (2026-08-24) — self-sufficiency v27.8: the Bin-2/3 "short reference line" text above
is reversed, and `State` joins the rung set as the 8th

Phase 00's real-corpus measurement (`plans/260824-1846-rebuild-spec-action-self-sufficiency-v27-8/`)
found a defect this ADR's own § "The three-bin rule for shared rules (§ 4.4)" text helped create:
100% of the corpus's bare-code defects sat in the `#### A<n>` heading line, with no gloss anywhere
else in the block. The Decision section above (unchanged, left as the record of what was decided
then) says a Bin-2/3-using action "carries a short reference line only" — read literally, that
licenses exactly the defect the measurement found. The correction, additive:

**What changes.** The three-bin rule for WHERE a rule's full citation + pseudocode lives is
untouched — Bin 2/3's one full block in § 4.4 stays the single place `**Source:**` and pseudocode
live. What changes is the *citing* action's own Rule rung: it must ALSO carry a plain-language
gloss inline, every time, not merely a `Used in:`/cross-cutting pointer. A code bare in the H4
context line with no gloss anywhere in its block is now a checked defect
(`FeatureSpec.action_ref_unglossed`, warning) — see
`references/feature-spec-researcher-contract.md` § "Self-sufficiency of the H4 context line" for
the full clause. This ADR's body text above is left as written (an ADR records the decision at
the time it was made); the corrected instruction lives in the authoring contract, cross-referenced
from `templates/technical-spec-template.md`, `references/code-formats.md`,
`references/verification-checklist-feature-spec.md`, `references/spec-authoring-contract.md`, and
`references/confidence-report-contract.md`.

**`State` joins `RUNG_LABELS` as the 8th rung**, between Result and Source:
`Who → FE → Request → BE → Rule → Result → State → Source`. Anchored on a document-level fact —
the feature carries a real `### … (SM-###)` heading block AND the action's own § 2 `Writes` cell
is non-`—` — never on prose-sniffing a transition from a method name (D3, unchanged). An earlier
design considered deriving `State` automatically from mermaid `stateDiagram-v2` edge labels; that
join was measured and dropped — it resolved only 2 of 16 real SM blocks on the corpus, because the
other 14 describe guards in prose with no bare method token to key off. `State` is authored by a
researcher fill pass reading the source, or it is omitted entirely (`FeatureSpec.state_rung_missing`,
warning, same fill-pending degradation window as `diagram_required_missing`) — never guessed and
never rendered as `N/A`/`None.` (that is `rung_empty_rendered`'s ground, unchanged). `State` is
not a citation source for A1: `derive_confidence_report.CITATION_RE` scores 0 matches against its
rendered form (measured against the real regex, not read off it) — the confidence-report
contract's "last entry is Source" statement stays true with `State` inserted before it.

**Where this was implemented.** `scripts/_spec_constants.py` (`RUNG_LABELS`),
`scripts/_action_thread_lib.py` (`_RUNG_LINE_RE`), `scripts/validate_feature_spec.py`
(`_check_action_thread`'s `state_rung_missing` branch, and the sibling
`_check_action_ref_unglossed`), and the doc surface named above.

## Addendum (2026-08-25) — v27.9.0: the last-bucket sink had a named cause — the code→capability
source was never stated

The "Bucket H3 … An action whose capability cannot be determined goes in the **last** bucket,
never the first" rule (Decision section, above) was correct and is unchanged by this addendum.
What was missing was never written down anywhere: **which source decides "cannot be
determined."** `assign_capability_and_detail`'s original implementation answered that silently by
re-deriving a code→capability map from `BR-`/`DEC-` rule codes found elsewhere in the document —
codes actions do not carry (actions carry `FR-`/`US-` codes). Every lookup missed, and the
documented last-bucket fallback fired on almost every action. Measured on the 43-feature
sharetribe corpus: **59 empty `### 3.N CAP-NN` sections**. This was not a bug in the fallback
rule — the fallback did exactly what it was told. It was a bug in an unstated silent input the
rule depended on, the same defect family `docs/decisions/ADR-0005.md`'s W5.6 finding already
named once for this repo: a rule believed to be running is not the same as a named source feeding
it.

**The fix.** `cap_code_map()` (new, `_feature_sot_capability_lib.py`) reads the twin
`functional-spec.md`'s own `## 2. Functional Capabilities` table — the `User Stories` /
`Requirements` / `Business Rules` columns — the same table `assign_codes` already trusts as the
single source of code ownership elsewhere in this pipeline. A code absent from all three columns
is, and only then is, undetermined. Re-measured on the same 43-feature corpus: **59 → 12** empty
sections, **zero** disagreements against the retired BR/DEC-derived map on the codes both maps
could resolve, and zero codes exclusive to either map. The residual 12 are honest: capabilities no
action happens to serve, not a resolution failure.

**The transferable lesson, restated for this instance.** A degradation path (last-bucket
fallback) is only as trustworthy as the thing that decides when to take it. Naming the decider in
the same sentence as the fallback — now done in `wire-format-contract.md` § 3 — is what keeps the
next implementer from re-deriving a silent, wrong source a second time.

**Where this was implemented.** `scripts/_feature_sot_capability_lib.py` (`cap_code_map()`, new),
`scripts/_feature_sot_structure_lib.py`, `scripts/_feature_sot_technical_lib.py`
(`assign_capability_and_detail`'s new `unbound_action_count` return, surfaced through
`ThreadComposeResult` and the `--migrate --only action-thread` operator-facing message), and
`plans/260824-1128-rebuild-spec-action-thread-v27-7/wire-format-contract.md` § 3 (the source now
named inline, alongside the unchanged fallback rule).

## Rejected / deferred alternatives

The full four-model comparison (Mẫu A "pure thread," Mẫu B "thread + shared foundation," Mẫu C
"table only," Mẫu D "progressive disclosure") and the diagram-ownership analysis live in
`plans/reports/brainstorm-260824-1027-technical-spec-action-thread.md` — not reproduced here.
Headline outcome: Mẫu B ("B-v" after the diagram-contract amendment) was chosen over Mẫu D
because D's "hot action" promotion threshold is itself a new gate that can fail silently
(the same defect class this ADR's "deferred criterion" section above is careful not to repeat),
while B adds no new silently-failable gate at the cost of a longer file. Mẫu A (uniform 7-rung
inline, no shared appendix) scored lowest on the study's own weighted rubric despite being the
literal original proposal — it optimized readability-within-one-action at the cost of
maintainability and file-level readability, the exact inversion of the stated priority order.
